# Kito website: plan

The site for Kito, the semantic version control system for swarms of AI
agents (source: `KitoOrg/kito`). It explains what Kito is, how to install
it, and where to download it. It lives in this repository, apart from the
code.

## Stack

- **Astro + Starlight**: static pages, Markdown/MDX content, built-in
  search (Pagefind), dark mode, sidebar navigation, i18n later if wanted.
- **Hosting**: GitHub Pages from a workflow in this repository. Pages on a
  *private* repository needs a paid GitHub plan; KitoOrg is on the free
  plan. Either this repository is made public at launch, or the site is
  deployed elsewhere (Cloudflare Pages, Netlify) from the private repo.
  See open questions.
- Node LTS, `pnpm`; no client-side framework beyond what Starlight ships.

## Pages

### 1. Home (`/`)

- One sentence: what Kito is. Version control where dozens of agents work
  in parallel on one repository and meet only real conflicts.
- Three or four ideas, each with a short example:
  - **Lanes**: every agent works in its own lane, declaring why and what
    it will change; lanes can be stacked on each other.
  - **Merged function by function**: two agents changing different
    functions of one file do not conflict.
  - **Git stays**: every checkpoint is a git commit; commits made with
    plain git come back in.
  - **Why code is the way it is**: every line keeps the reason it was
    written for, told to the next agent before it changes it.
- A short terminal session (from `docs/demo/` in the kito repository).
- Buttons: Install, Read the docs, GitHub.

### 2. Install (`/install`)

- Linux and macOS. Windows through WSL (Ubuntu), with the clone kept in
  the Linux file system.
- **Install script**: `curl -fsSL https://<domain>/install.sh | sh`,
  which picks the archive for the platform from the latest GitHub
  Release, checks its SHA-256 and puts `kito`, `kitod`, `kito-mcp` and
  `kito-server` in `~/.local/bin`.
- **Archives** by hand (link to the download page).
- **From source**: Rust 1.90+, `cargo build --release -p kitod -p kito-cli
  -p kito-mcp -p kito-server`.
- Requirements: git; Linux 5.13+ for confined checks (Landlock); language
  servers, optional, for rename propagation.
- First steps after installing: `kito init`, Claude Code / MCP setup.

### 3. Download (`/download`)

- The latest release: version, date, archives per platform
  (`linux-x86_64`, `linux-aarch64`, `macos-arm64`, `macos-x86_64`) with
  their SHA-256, and the release notes.
- Older releases below, from the GitHub Releases API, read **at build
  time** (no JavaScript call at visit time); a release published in the
  kito repository triggers a rebuild of the site (`repository_dispatch`).

### 4. Docs (`/docs/...`)

- **Getting started**: install, `kito init` in a project, a first lane,
  integrate, see the git commit.
- **Concepts**: lanes and scopes; the intent board and overlaps;
  checkpoints and the git export; conflicts and decisions; the why graph;
  lanes on lanes; permanent lanes (`staging`, once phase 16 is out).
- **Guides**: Claude Code and other MCP clients; a team on `kito-server`
  (TLS, users, roles); a protected main lane and approvals; git both ways
  (push, pull); checks, batching and the sandbox; importing a git
  repository.
- **Reference**: CLI commands (generated from `kito <command> --help`),
  `.kito/config.toml` (every key, default and meaning), MCP tools, the
  events of `kito watch`.
- **Design**: links to the ADRs, the decisions log and the phases, which
  stay in the kito repository where they are written with the code.

## Where the docs' content comes from

- User-facing docs are written here.
- The command and configuration references are generated by a script that
  runs the released binaries (`kito --help`, the default
  `.kito/config.toml`), so they match a version. Pages say which version
  they describe.
- Design documents stay in the kito repository and are linked, not copied.

## What the kito repository needs first

1. **A release workflow**: on a `v*` tag, build the four binaries for the
   four platforms, pack them with a checksum, publish a GitHub Release.
2. **`install.sh`** in the kito repository, served by the site.
3. **A changelog** per release, from `docs/phases.md`.
4. Releases readable by visitors: the download page and `install.sh`
   need the release archives to be public. While `KitoOrg/kito` is
   private, they are not (see open questions).

## Milestones

1. **Skeleton**: Astro + Starlight, home, install, three Getting started
   pages, deploy from `main`.
2. **Concepts and guides**: the pages above, with examples from the demos.
3. **Reference**: generation scripts for CLI, configuration, MCP tools.
4. **Download**: release workflow in kito, release data at build time,
   install script.
5. **Launch**: domain, repositories made public (or releases moved to a
   public repository), first tagged release.

## Open questions

- **Domain** (and whether `install.sh` is served from it or from GitHub).
- **Public or not at launch**: GitHub Pages and downloadable releases both
  need public repositories on the free plan. Alternatives: a public
  `KitoOrg/releases` repository holding only the archives, and a host
  other than GitHub Pages for the site.
- **Name and logo**: a mark for the home page and the favicon.
- **Analytics**: none, or a privacy-friendly one.
